# 受管研究对话顺序设计

## 意图

让研究请求按用户可理解的因果顺序展示：AI 先说明已创建的研究配置，用户确认后展示研究工作流，工作流成功后在统一的“研究成果”区域展示脚本和运行结果。避免当前“工作流、运行结果、迟到的 AI 说明、脚本”的倒序感。

## 目标

- `prepare_study` 成功时，先持久化并发布一条确定性的 AI 确认语，再发布研究配置卡。
- 配置成功后的 provider 收尾文本不再作为迟到的独立 assistant 消息写入，避免用户确认后穿插到工作流中。
- 成功工作流把对应的受管脚本卡和运行结果卡归入同一个“研究成果”区域，并保持脚本消息原有稳定 ID 和运行记录定位能力。
- 刷新、历史回放、分页锚定和 SSE 实时消息得到相同顺序。

## 非目标与反目标

- 不按消息类型或可变时间戳全局重排历史消息。
- 不修改消息表 schema、公共路由或稳定消息类型。
- 不合并或删除脚本资源、脚本消息、运行结果，也不改变失败工作流的日志、分析、修正或重试行为。
- 不让前端根据文案猜测消息关系。

## 约束

- 消息仍按稳定数值 ID 排序，revision 更新不改变消息位置。
- 脚本消息必须继续作为运行记录的 `scriptMessageId` 锚点。
- 只有同时位于当前历史窗口、且脚本资源 ID 与成功工作流 `scriptId` 一致的脚本消息才视觉归组；缺少任一消息时不得隐藏另一条消息。
- 普通手写、上传和非受管脚本继续独立展示。

## 方案比较

1. **按类型或时间戳重排。** 改动小，但 operation card 的时间戳会随 revision 更新，且不同工作流、分页窗口和普通脚本可能错配，因此不采用。
2. **等待 provider 收尾后才允许确认。** 能保留模型收尾文本，但会让已就绪配置继续等待模型，增加延迟并引入新的“对话完成”状态，因此不采用。
3. **确定性确认语 + 因果归组。** `prepare_study` 在配置卡前写入简短 assistant 确认语，ChatService 忽略该工具成功后的 provider 尾声；前端按工作流 `scriptId` 归组既有脚本消息。该方案不改变稳定资源和数据库顺序，且实时与回放一致，采用此方案。

## 行为设计

### 规划阶段

`prepare_study` 创建配置成功后写入：

> 已为您创建“{研究标题}”研究配置卡（ID: {配置 ID}），请在卡片中检查并确认输入、参数和结果。

随后写入研究配置卡。工具只有在确认语和配置卡都已写入后才返回成功。工具成功之后由 provider 生成的尾声文本不再持久化；工具成功之前已经产生的说明文本仍保留。provider 在工具成功后关闭或报错时，不追加通用 Agent 失败提示，因为确定性确认语和配置卡已经持久化。

### 执行与成果阶段

研究配置确认后，工作流卡仍在原位置原地更新。成功终态时，前端在工作流卡下显示一个 `研究成果` 区域：

1. 对应的受管脚本卡；
2. 对应 run 的运行结果卡。

脚本数据库消息不移动也不删除。前端仅在渲染投影中把匹配的独立脚本消息收进成果区域，并在嵌入位置保留 `data-message-id`，使运行记录定位、焦点和高亮仍指向脚本卡。锚定窗口只有脚本而没有工作流时，脚本仍独立显示。

## 验证

- Rust 行为测试证明 assistant 确认语的消息 ID 小于配置卡，provider 尾声不重复出现，provider 收尾失败仍保留成功确认语。
- 前端投影测试证明只归组成功工作流的匹配脚本，普通脚本、失败工作流脚本和缺失配对消息不被隐藏。
- 组件测试证明成果区顺序为脚本后运行结果，并保留脚本消息定位锚点。
