# 无固定超时的引擎执行与用户取消设计

## 意图

案例规模差异很大，固定墙钟时间会把大型正常计算误判为失败。所有生产 `tensoreval` 调用都应持续到引擎正常结束、主动报错、触发结果安全限制或服务停止；普通脚本运行和受管工作流还必须有可见、可靠的用户取消入口。

## 目标

- 删除所有生产 `tensoreval` 调用的执行时间上限以及 `TENSOREVAL_TIMEOUT_MS` 配置。
- 保留现有结果目录数量、单文件大小、总大小、普通文件和路径边界监控。
- 受管工作流继续使用现有取消接口；为普通运行新增用户级取消接口和运行记录按钮。
- 取消排队中或执行中的任务时释放 scheduler 名额；执行中取消必须终止整个进程组并清理未发布结果。
- 取消操作按用户隔离、幂等且能抵抗“取消与成功同时发生”的竞态。
- 历史 `engine_timeout` 记录仍可读取，但新的生产执行不再产生该错误码。

## 非目标

- 不实现暂停、断点续算、自动扩缩容或按案例估算完成时间。
- 不根据输入行数动态计算超时，也不保留运维侧隐藏超时。
- 不移除测试代码、HTTP 客户端、LLM 调用或失败分析自身用于防止自动化和网络永久等待的超时；本设计删除的是生产 `tensoreval` 子进程执行超时。
- 不为案例检查、导入、投影或派生分析新增独立取消接口；这些任务只能完成、主动失败、触发结果安全限制或随服务停止而终止。
- 不改变服务重启后的恢复语义：进程重启时尚未完成的任务仍收敛为 `service_restarted`。

## 方案取舍

### 方案 A：按案例规模动态计算超时

可限制失控任务，但规模、求解算法、时序长度和收敛难度并非线性关系，仍会误杀合法计算，也需要长期维护经验参数，因此不采用。

### 方案 B：默认无限、保留可选运维超时

能提供紧急保护，但仍保留一条会自动终止合法任务的生产路径，不符合已确认的“只能完成、主动失败、触发结果安全限制、服务停止或在支持的任务上由用户取消”语义，因此不采用。

### 方案 C：彻底移除生产引擎执行超时，并完善仿真取消

这是已选择的方案。所有生产引擎调用的资源安全由现有结果监控和并发/队列上限负责；普通仿真和受管工作流可由用户取消，案例检查、导入、投影和派生分析不新增取消能力。

## 后端设计

### 引擎边界

- 从运行配置、应用组装、`ProcessEngine`、`RunSpec` 以及案例检查/导入/投影 spec 中移除生产引擎 timeout 字段和默认值。
- `run_command` 不再使用 `tokio::time::timeout`，只等待子进程退出或结果目录监控报错。
- 删除创建 `engine_timeout` 的 adapter 分支、稳定错误码注册和“超时不可修正”特判；其他基础设施错误及结果合同错误语义不变。
- 保留 `ProcessGroupGuard`。任何持有引擎 future 的任务被用户取消、会话删除或服务关闭时，future drop 必须杀掉整个进程组并删除未完成结果目录。
- 测试外围可继续使用 `tokio::time::timeout` 作为测试失败上限，但不得把测试等待上限重新变成生产引擎截止时间。

### 普通运行取消

- 新增 `POST /api/runs/{id}/cancel`，handler 使用 `///` 注释说明用户边界、幂等和竞态语义。
- 跨用户、已删除和不存在的 run 统一返回 404。排队中、运行中的 run 被取消后返回 200；重复取消返回相同终态。已经成功或因其他原因失败的终态 run 保持不变并返回 200。
- 该路由只取消普通 run。若 run 带有 `managedWorkflowId`，返回 409 `managed_run_cancel_via_workflow`；前端和其他客户端应改调对应 workflow 的取消接口，避免两个服务竞争写同一终态。
- 普通运行 worker 增加按 run ID 保存的 cancellation sender。信号同时覆盖 scheduler 排队等待和 active execution；不能只在获取 semaphore 时检查。
- 数据库不扩展 `simulation_runs.status` 枚举。用户取消写为 `status=failed`、取消阶段和公开 `error.code=cancelled_by_user`，以避免重建 SQLite 表；API 和前端把该组合展示为“已取消”，而不是一般失败。
- 取消落库与 worker 完成均使用带当前状态条件的 compare-and-set。取消先取得终态的一方获胜：若取消成功落库，后续成功发布不得覆盖；若成功已经原子发布，迟到的取消保持成功终态。
- 取消执行中的 run 时丢弃引擎 future，由进程守卫完成 kill 和临时结果清理；任何结果都不得部分发布。
- sender 在普通 run 到达任一终态后移除，防止注册表增长。会话级取消继续生效，并复用相同的执行终止路径。

### 受管工作流

- 保留 `POST /api/workflows/{id}/cancel`、`cancelled_by_user` workflow 状态和当前前端卡片。
- 去掉 worker 的 engine timeout 参数及相关不可修正分支。脚本生成、修正预算和结果合同验证不变。
- workflow 关联的 provisional run 应继续随 workflow 终态收敛；运行记录中的取消入口根据 `managedWorkflowId` 调用 workflow 取消接口，避免出现两个互相竞争的取消事务。

## 前端设计

- API client 增加 `cancelRun(id)`。
- 运行记录对 `queued`/`running` 项显示“取消”：普通 run 调用新 run 接口；带 `managedWorkflowId` 的 run 调用现有 workflow 接口。
- 点击后按钮立即进入“取消中…”并禁用，成功后刷新运行列表；请求失败恢复按钮并显示错误通知。
- `cancelled_by_user` 在运行记录中显示“已取消”，详情显示取消时间和已运行时长，不使用红色“求解失败”文案。
- 已成功、一般失败、已取消或服务重启的终态不显示取消按钮。

## API、错误码与兼容性

- 新增公共路由 `POST /api/runs/{id}/cancel`，同步更新 API 设计、前端 DTO/客户端、功能目录和行为测试。
- 从当前生产错误枚举中移除 `engine_timeout`；数据库内历史错误 JSON 不迁移、不重写，读取时继续通过兼容兜底展示。
- `cancelled_by_user` 成为普通 run 可公开的稳定错误码。它表示用户动作，不进入失败分析，也不触发 Agent 修正。
- 删除部署文档中的 `TENSOREVAL_TIMEOUT_MS`。若部署环境仍提供该变量，服务忽略它且不因此启动失败。

## 验证

- 进程适配器测试：长时间 helper 不会自动结束；drop/cancel 会终止父子进程组并清理结果目录；结果监控失败仍会终止进程。
- 应用测试：普通 run 在排队和 active 两阶段均可取消；取消释放并发名额；取消不触发失败分析；无部分结果；终态和重复取消幂等。
- 竞态测试：取消与成功发布并发时只能保留一个终态，且 artifact 引用计数一致。
- 用户隔离测试：其他用户取消返回 404。
- 受管工作流回归：生成、修正、用户取消、会话删除和服务重启语义保持正确。
- 前端测试：按钮可见性、取消中状态、普通/受管 endpoint 分流、成功刷新、失败恢复和“已取消”展示。
- 更新 `docs/development-status.md`、`docs/api-design.md`、`docs/v4-deployment.md`、`docs/integration-testing-design.md` 与 `integration-tests/catalog/features.yaml`，移除生产引擎超时行为覆盖，并加入无限时执行与普通运行取消的行为追溯。

## 实施约束

- 所有子进程操作仍只允许位于 `backend/src/adapters/`。
- 取消不能绕过用户隔离，也不能暴露 PID、路径、命令或原始 stderr。
- scheduler 的并发和队列上限保持不变；无限运行可能长期占用名额，这是已接受的产品语义，用户通过运行记录取消。
- 案例检查、导入、投影或派生分析若长期不结束，只能等待其完成、主动失败或通过停止服务终止；这是已确认的产品取舍。
- 实现者可自行决定 cancellation registry 的具体内部类型和模块位置，只要满足上述持久化、竞态和清理语义。
