# 研究工作流失败诊断设计

**日期：** 2026-11-01

## 目标

研究工作流执行失败后，在原进度卡片内紧跟展示可复核的失败诊断，而不是要求用户再到运行记录中查找。诊断必须在刷新和恢复历史后仍然存在。

## 用户界面

- 失败工作流首先展示“失败诊断”区域。
- “引擎输出”保持 stdout/stderr 的原始文本格式、换行、退出码和执行耗时；所有内容在下发前经过现有脱敏边界。
- “大模型分析”只输出面向用户的结构化诊断摘要，分为已确认事实、可能原因、仍未知信息和建议动作；事实必须引用具体日志片段，不输出模型思维链。
- 大模型分析失败时仍展示引擎输出，并明确标记“智能分析暂不可用”。
- “自动修正记录”默认折叠。每次记录显示依据、是否产生脚本实质变化以及重试结果；相邻脚本内容哈希相同时明确显示“未产生实质修改”。
- 浏览器可以把当前 API 返回的完整脱敏日志下载为文本文件；如果服务端只保留了截断内容，界面必须明确标记，不能声称下载的是完整日志。

## 数据与边界

- 不新增可变资源；诊断随不可变 workflow attempt 持久化。
- 继续使用 `workflow_attempts.result_diagnostics_json` 保存结构化公开诊断，避免改变 V4 schema；原始审计 artifact 仍只用于服务端审计，不直接公开。
- API 只返回脱敏后的公开日志，不返回审计 artifact ID、服务器路径、命令或密钥。
- 引擎失败诊断包含现有稳定错误码，并新增可选字段：`analysis`、日志元数据和修正评估。旧记录缺少这些字段时前端兼容降级。
- 大模型只接收已脱敏 stderr、受控 diagnostic、冻结合同摘要和当前脚本；输出严格限制长度和条目数量。

## 大模型分析合同

分析结果为受控 JSON：

```json
{
  "summary": "一句话结论",
  "facts": [{ "statement": "已确认事实", "evidence": "stderr: ..." }],
  "possibleCauses": [{ "statement": "可能原因", "evidence": "stderr: ..." }],
  "unknowns": ["仍需确认的信息"],
  "recommendations": ["下一步动作"]
}
```

解析失败、字段越界或模型不可用时不阻断自动修正和最终失败落库；只记录公开的 unavailable 状态，不把 provider 错误原文下发。

## 验收标准

1. 引擎失败后 workflow detail DTO 带有持久化的结构化诊断和脱敏日志元数据。
2. 诊断模型不可用时，工作流仍按原逻辑修正或失败，日志仍可见。
3. 失败卡片直接展示格式化日志和结构化分析，自动修正记录默认折叠。
4. 相同脚本哈希的修正尝试明确标记为“未产生实质修改”。
5. 后端、前端测试以及设计文档和功能目录同步更新。
