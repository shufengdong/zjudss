# 研究配置终态同步设计

## 意图

配置卡被确认后，持久化消息和后续 Agent 上下文必须立即反映 `confirmed`，避免 Agent 把已执行的配置误认为仍待确认，也避免用户再次发起同一研究时看不到新配置卡。

## 目标与非目标

- 确认成功后更新同一条 `study-config` 消息并发布终态事件。
- Agent 历史只注入数据库中仍可编辑的最新配置，消息 payload 不能单独决定当前状态。
- 回归覆盖“确认后再次研究不会复用旧配置上下文”。
- 不改变确认授权、workflow 创建、前端卡片结构或自然语言确认边界。

## 约束

- `study_configurations` 是配置状态的权威来源。
- 卡片消息仍按 configuration ID 原位 upsert，不创建重复卡片。
- 跨用户和不存在资源继续统一返回 404；确认事务成功不能被后续消息发布失败回滚或重复执行。

## 方案

采用双层修复：确认 API 在领域事务成功后读取配置并发布 `confirmed` 卡片；聊天历史构建同时用权威配置记录校验消息中的候选卡片。只修确认发布会让历史依赖事件写入绝对成功；只修历史过滤则会留下 UI 和持久消息的旧状态。两者结合保证展示一致性并提供防御性校验。

未采用前端本地伪造 `confirmed` 状态，因为刷新后仍会读取旧消息，也无法修正 Agent 上下文。未采用仅加强 Prompt，因为错误上下文本身仍把旧卡声明为当前配置。
