# 研究结果双入口选择设计

## 意图

修复研究配置已经进入 `ready_to_confirm` 后，用户既不能在配置卡修改结果，也不能用自然语言修改结果的死角。用户应能在最终确认前通过配置卡或自然语言选择结果；无论使用哪种入口，都必须保留“确认并生成脚本”这一固定最终门禁。

## 目标

- `collecting_inputs` 与 `ready_to_confirm` 状态都展示可编辑的结果选择。
- 用户说“bus_voltage，summary”时，Agent 能把当前未确认配置的结果更新为这两个稳定结果名称。
- 更新使用配置 ID、准确 revision 和目录声明的结果名称，沿用现有并发冲突与结果约束校验。
- 更新成功后 durable 配置卡原位升级 revision，摘要立即显示最新选择。
- Agent 只能修改结果集合，不能通过自然语言确认配置、生成脚本或启动运行。

## 非目标

- 不允许 Agent 修改输入绑定、Struct 参数或最终确认状态。
- 不新增独立“仿真结果页面”，不改变运行完成后的结果工作台。
- 不引入自由格式配置 patch，也不绕过现有 `PUT /api/study-configurations/{id}/results` 业务服务。

## 约束

- 工具只接受当前会话中的稳定配置 ID、`expectedRevision` 和目录内的结果名称。
- 工具必须拒绝已确认、失效或取消的配置，并保留用户隔离与 404 语义。
- revision 冲突返回现有 `configuration_stale`，Agent 必须重新读取当前配置，不能猜测新 revision。
- 新工具、行为和公共合同同步更新 manifest、skill index、设计文档、功能目录及自动化行为测试。

## 方案比较

1. **仅修复前端复选框。** 改动最小，但 Agent 仍会在自然语言对话中邀请用户选择却无法执行，不能满足双入口体验。
2. **增加专用结果选择工具并修复前端（采用）。** 工具权限窄，复用现有服务校验；配置卡仍是确定性后备入口，自然语言成为便捷入口。
3. **增加通用研究配置 patch 工具。** 扩展性高，但会把输入、参数和确认边界一起暴露给 Agent，权限过宽且违背固定确认门禁。

## 交互与错误处理

- 配置卡在 `ready_to_confirm` 时显示结果选择区和最终摘要；用户保存新结果后以服务端响应替换整张卡。
- Agent 更新成功后明确列出已选择结果，并提示仍需点击“确认并生成脚本”。
- 未找到唯一当前配置、结果名无效、revision 过期或配置已终止时，不宣称成功；展示稳定错误并引导用户回到最新配置卡。
- 结果列表至少保留一个结果，顺序与用户表达或卡片勾选顺序一致，重复项由服务端拒绝或规范化为现有合同定义的合法集合。

## 验证

- 前端组件测试覆盖 `ready_to_confirm` 下修改 `bus_voltage + summary`，并验证摘要使用更新后的 revision/选择。
- 后端工具测试覆盖成功更新、错误 revision、未知结果、跨会话/用户与终态拒绝。
- Agent/端到端测试覆盖自然语言选择后 durable 卡更新，但没有创建 workflow 或 run。
- 功能目录与工具清单追溯新工具和上述行为。
